# Bridge-X Project Brief

## 1. 출발점

2025년 8월의 BridgeNote는 다국어 회의에서 단순 번역을 넘어 문화적 맥락과 오해 가능성을 보완하는 서비스였습니다.

기존 경험:

- 언어·문화·직무 프로필
- 실시간 음성, 자막, 번역
- 발화 의도와 청자의 오해 가능성 분석
- 위험도, 조언, 재작성 문장 제공
- 회의 종료 후 맥락이 포함된 회의록 생성
- React/Vite/Zustand/Tailwind 프런트엔드, Spring 백엔드, FastAPI AI 계층 연동 경험

여기서 남은 핵심 통찰은 “번역 정확도”보다 **서로 다른 관점 사이에서 맥락이 손실되는 문제**였습니다.

## 2. 냉정한 방향 판단

Bridge-X는 “문화 번역의 기능 확장판”으로 한정하지 않습니다. 제품의 계보는 BridgeNote에서 이어가되 문제 정의는 새로 시작합니다.

- 언어 번역은 회의 도구의 기본 기능으로 빠르게 흡수되고 있습니다.
- 문화는 국적만으로 결정할 수 없으며 상황, 관계, 목표, 개인 선호가 함께 작동합니다.
- 범용 에이전트 생성·연결 시장은 이미 많은 기업과 프레임워크가 경쟁하고 있습니다.
- 다중 에이전트는 항상 더 낫지 않습니다. 순차 의존성이 높은 작업에서는 오류 전파와 조정 비용이 커질 수 있습니다.

따라서 Bridge-X의 범주는 **Agent Handoff & Context Coordination**입니다.

## 3. 문제 정의

서로 다른 직무와 도메인을 맡은 AI 에이전트가 협업할 때 산출물은 전달되지만 다음이 자주 손실됩니다.

- 왜 이 결론을 냈는지
- 무엇이 사실이고 무엇이 가정인지
- 어떤 제약을 고려했는지
- 다음 역할이 무엇을 완료해야 하는지
- 역할 간 요구사항이 어디서 충돌하는지
- 어떤 결정을 사람이 내려야 하는지

핵심 문제 문장:

> 여러 전문 에이전트를 사용하는 팀은 에이전트 간 전달 과정에서 의도, 근거, 제약 및 완료 기준이 손실돼 잘못된 결과를 늦게 발견한다.

## 4. 제안하는 제품

### Bridge-X

사람·직무·전문 에이전트 사이의 의도, 근거, 제약, 완료 기준을 보존하고 검증하는 협업 품질 계층입니다.

### 핵심 차별점: Context Handoff

각 에이전트의 자유 형식 응답을 다음 항목을 가진 핸드오프 계약으로 변환합니다.

- 목적과 대상 역할
- 산출물
- 주장별 근거·출처·신뢰도
- 사실과 가정
- 제약 조건
- 열린 질문
- 완료 기준
- 사람의 결정이 필요한 항목

Bridge-X는 여러 핸드오프를 비교해 충돌, 누락, 근거 부족, 목표 이탈을 드러냅니다. 자동 합의보다 **검증 가능한 불일치**를 우선합니다.

## 5. 현재 MVP: Spec Preflight

모든 협업 과정을 한 번에 바꾸기보다, PM이나 의뢰자의 업무 요청이 디자인·개발·리스크 등 실행 역할로 넘어가는 순간부터 해결합니다.

1. 목표, 원본 요청, 대상 역할, 비협상 제약을 입력합니다.
2. Role Lens가 같은 요청을 역할별 실행 관점으로 해석합니다.
3. Meaning Diff가 보낸 의도와 받을 해석의 차이를 원문 근거와 함께 보여줍니다.
4. 사람이 결정해야 할 질문을 Decision Ledger로 분리합니다.
5. Shared Contract와 Receiver Receipt로 실행 합의와 이해 확인을 남깁니다.

이 사용 사례는 짧은 시연으로 가치가 보이고, 실제 재질문·재작업 감소를 측정할 수 있으며, 현재 프로토타입과도 정확히 일치합니다.

### 확장 비전: AI Product War Room

Spec Preflight에서 검증한 Context Handoff 계약을 Research·Product·UX·Engineering·Risk·Verifier 에이전트의 산출물에도 적용합니다. 핵심은 에이전트 수가 아니라 각 산출물의 근거·가정·제약·완료 기준과 사람의 결정을 다음 역할까지 보존하는 것입니다.

## 6. 초기 사용자 가설

첫 고객은 “많은 에이전트를 운영하는 대기업”보다 여러 AI 도구와 모델의 결과를 복사·붙여넣으며 일하는 소규모 제품 팀, 에이전시, 창업 팀에 가깝습니다.

이들은 이미 문제를 겪고 있으며 다음 행동을 수작업으로 합니다.

- 같은 배경을 여러 AI에 반복 설명
- 결과를 문서로 옮겨 합치기
- 서로 다른 답변의 충돌을 직접 판단
- 빠진 요구사항을 뒤늦게 발견
- 최종 의사결정 근거를 재구성

## 7. MVP 범위

### 포함

- 하나의 업무 요청 handoff 분석
- 송신 역할과 1~6개 수신 역할
- 목표·제약·원문 입력
- 역할별 해석과 Meaning Diff
- `Go / Revise / Stop` 제안
- Shared Contract와 Decision Ledger
- Receiver Receipt 확인
- API가 없어도 작동하는 재현 가능한 데모 모드

### 제외

- 누구나 임의의 에이전트를 만드는 범용 빌더
- 완전 자율 실행
- 모든 SaaS 도구 연동
- 문화·국적 기반 성향 판정
- 복잡한 에이전트 마켓플레이스
- 처음부터 거대한 그래프 오케스트레이션

## 8. 반드시 검증할 가설

1. 사용자는 에이전트 생성보다 결과 통합과 충돌 확인에 더 큰 불편을 느끼는가?
2. Context Handoff가 실제 재작업과 누락을 줄이는가?
3. 어떤 항목까지 자동 판정하고 어디서 사람 승인이 필요한가?
4. 검증 비용과 토큰 비용보다 절감되는 시간이 큰가?
5. 제품 기획 외에 리서치, 개발 인수인계, 컴플라이언스 중 다음 확장 영역은 무엇인가?

## 9. 주요 위험

- 범용 오케스트레이션 도구로 보이면 기존 제품과 차이가 약해집니다.
- 에이전트 수를 늘리는 것 자체가 품질 향상을 보장하지 않습니다.
- 검증 에이전트도 틀릴 수 있으므로 출처 추적과 사람 승인 구조가 필요합니다.
- 문화 해석을 고정된 국가 특성으로 일반화하면 정확도와 윤리 모두 위험합니다.
- 초기에 너무 많은 직무와 연동을 지원하면 제품 가치보다 설정 복잡도가 커집니다.

## 10. 성공 지표 초안

- 핸드오프 후 재질문 횟수 감소
- 누락 요구사항의 조기 발견률
- 충돌 발견 후 수정된 결정 비율
- 최종 브리프 작성 시간 감소
- 근거가 연결된 핵심 주장 비율
- 사용자 승인 전 자동 실행 비율이 아니라, 승인 시 판단에 걸린 시간

## 11. 제품 원칙

- 오케스트레이션보다 맥락 보존
- 대화량보다 검증 가능한 산출물
- 자동 합의보다 명시적 충돌
- 에이전트 수보다 적절한 역할 분해
- 자율성보다 추적 가능성과 승인
- 문화는 판정값이 아니라 질문을 촉발하는 신호
